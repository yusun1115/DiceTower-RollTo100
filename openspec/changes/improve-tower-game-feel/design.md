# Design

## Context

동기는 `proposal.md`를 참조한다. 현재 구현에서 확인한 접근 제약은 다음과 같다.

- `apps/client/src/main.ts`는 DOM 구성, 서버 메시지 처리, 입력, Canvas 2D 렌더링, 효과음을 한 파일에 담고 있다. `draw()`는 상태 메시지를 받을 때 호출되고, 현재 `requestAnimationFrame` 루프는 입력 전송만 담당한다.
- `apps/server/src/server.ts`는 50ms 간격으로 세션을 갱신한다. `SessionHost.tick()`은 변화가 없는 대기실에도 스냅샷을 보낸다. 클라이언트의 `renderActions()`와 `renderShop()`는 그때마다 버튼을 제거하고 다시 만들기 때문에 누르기/떼기 사이의 갱신과 키보드 포커스 유지가 취약하다. 이는 소스에서 발견한 위험이며 현재 공개 페이지에서 재현한 결과로 주장하지 않는다.
- `SessionEngine.roll()`은 이동과 `enterFloor()`를 같은 명령에서 처리한다. 확인 응답 시에는 전투 타이머가 이미 진행될 수 있다. 사망은 하트를 복구하고 개인 런타임을 지우며, 마지막 적 처치는 다음 턴으로 넘어가므로 스냅샷 차이만으로 모든 결과를 복원할 수 없다.
- 현재 `draw()`는 항상 로컬 `playerId`의 전투를 선택해 상대/CPU의 활성 전투와 다른 장면을 그릴 수 있다. 표현은 `activePlayer`의 런타임을 기준으로 바꿔야 한다.
- `ITEM_DEFINITIONS`에는 한국어 이름·희귀도·효과·위험·지속시간이 있지만 HUD와 상점은 주로 `itemId`를 그대로 출력한다.
- `apps/client/public/assets/`에는 Git 미추적 상태의 주사위, 캐릭터/애니메이션, 던전, 상점, 탑, 아이콘 PNG가 있다. `dice-faces.png`는 3×2 배치이며 어두운 배경이 포함되어 있다. `player-hero-animations.png`는 4×4에 가까운 포즈 배치지만 프레임별 외곽 크기와 발 위치가 다르다. 탑 배경은 세로로 긴 석조 계단 이미지다. 실제 연결은 없고, 균일한 셀 분할이나 투명 배경을 가정할 수 없다.
- 기반 게임 변경은 37개 작업이 완료되었지만 정식 `openspec/specs/`에는 아직 명세가 없다. 이 변경은 기존 변경의 규칙 명세를 수정하거나 아카이브하지 않고 표현 기능 3개를 별도로 추가한다.

## Goals / Non-Goals

**Goals:**

- 화면은 프레임 단위로 부드럽게 움직이고, 판정은 기존 서버가 계속 결정하는 경계를 유지한다.
- 결과가 즉시 다음 상태로 넘어가더라도 한 번의 행동에 한 번의 피드백을 연결한다.
- 게임의 주된 박자를 주사위 착지, 층 도착, 타격, 보상, 턴 교대로 만들고 강한 연출은 그 순간에 집중한다.
- 새 표현 필드가 없는 서버, 이미지 실패, 음향 차단에서도 기존 게임 흐름을 계속 사용할 수 있게 한다.

**Non-Goals:**

- 표현을 위해 새 전투 대기 상태, 연출 완료 확인 명령, 서버 일시정지, 판정 지연을 넣지 않는다.
- 위치 보간·피격 반응·잔상을 물리 이동이나 클라이언트 판정으로 사용하지 않는다.
- 리소스 전체를 다시 제작하거나 모든 원본 시트를 한 번에 로딩하는 파이프라인을 만들지 않는다.

## Decisions

### 1. 기존 아트를 활용한 석조 탑 테마

테마는 어두운 석조/목탄색 바탕, 금빛 주사위·전리품, 청록 1P·주황 2P 표식, 붉은 위험, 보랏빛 유령으로 정한다. 색상뿐 아니라 `1P`/`2P`, 아이콘·실루엣·문구로 상태를 구분한다. 전투 시작 후 큰 제목은 작은 게임명으로 접어 공간을 확보한다. 한국어 본문은 읽기 쉬운 폰트 스택을 사용하고 제목만 장식적인 서체 톤을 적용한다.

캐릭터는 발 위치 기준으로 배치하고 지면 그림자와 작은 충돌 위치 표식을 사용한다. 그림의 장식 외곽이 실제 충돌 반경으로 오해되지 않게 한다. 던전 타일, 장벽, 상자, 몬스터를 구분하며 보스는 일반 적보다 명확한 크기·체력 표시를 가진다.

필요한 파일만 자산 매니페스트에 등록한다. 각 프레임의 source rectangle, 발 피벗, 표시 크기, 상태별 프레임 목록을 명시한다. 주사위는 6면의 source rectangle을 사용해 배경이 포함된 원본도 카드의 어두운 받침에 자연스럽게 맞춘다. 캐릭터는 걷기/공격/피격/사망에 필요한 프레임만 먼저 연결한다. 부족한 방향은 좌우 반전 또는 명확한 대체 그림으로 처리한다.

**대안:** 효과만 단순 도형 위에 붙이는 방법은 화면의 밋밋함을 충분히 해소하지 못한다. 전면 아트 재제작은 이미 존재하는 재료에 비해 범위와 로딩 부담이 크다. 사용 가능한 원본을 선별하고 효과는 Canvas/CSS로 만든다.

### 2. 상태 수신과 화면 갱신의 분리

메시지 처리기는 최신 상태와 이전 상태, 수신 시각, 새 표현 이벤트를 기록한다. 하나의 프레임 루프가 입력 전송의 기존 간격을 유지하면서 Canvas 렌더링, 효과 TTL, 애니메이션 시각을 갱신한다. 위치는 동일 세션·턴·전투 장면 안에서만 약 50ms의 제한된 보간을 적용한다. 대시, 사망, 새 층, 새 턴에서는 이전 좌표와의 보간을 끊는다. 타이머·하트·코인·층·턴의 기준값은 항상 최신 서버 상태다.

DOM은 최초에 만들고 변한 값만 갱신한다. 준비·주사위·물약 버튼은 유지하고 disabled/text 상태를 바꾼다. 상점 버튼은 해당 상점의 재입고 세대와 slotId를 함께 키로 사용해 다른 재고가 기존 포커스에 잘못 연결되지 않게 한다. 판매된 슬롯만 제거하거나 비활성화하고 남은 상품의 포커스는 유지한다.

모듈 경계는 `hud.ts`, `renderer.ts`, `assets.ts`, `presentation/event-router.ts`, `journey.ts`, `effects.ts`, `audio.ts`, `preferences.ts`로 분리하는 것을 기본으로 한다. `main.ts`에는 연결·상태 전달·루프 조립을 남긴다. 작은 공통 로직은 필요 이상으로 분리하지 않는다.

**대안:** 서버 전송 빈도를 높이면 대역폭이 늘면서도 버튼 교체와 독립 연출 문제는 남는다. 프레임 렌더링과 안정적인 DOM이 현재 구조에 직접 대응한다.

### 3. 작은 서버 표현 이벤트와 클라이언트 중복 제거

`SessionState`에 선택적인 `presentationEvents` 필드를 추가한다. 기존 `ClientMessage` 행동 계약은 그대로 유지한다. 이벤트는 세션 내 단조 증가 sequence, 세션 ID, 발생 참가자, 턴, 층, 종류, 필요한 작은 payload를 가진다. 현재 게임 메서드가 성공한 뒤 결과를 기록하며, 입력 메시지 자체를 성공 이벤트로 사용하지 않는다.

필요한 사건은 주사위 확정, 공격/대시 수락, 적 피해/처치, 플레이어 피해/회복/사망, 상자 개봉/아이템 획득/구매, 무기 만료, 층 클리어, 턴 시작, 유령 출현, 상점 재입고, 승리다. payload는 사건 발생 당시 좌표·피해량·보상량·대상 ID와 이동 전후 층 등으로 제한한다. 삭제될 런타임의 최종 타격·사망 위치와 원인을 상태 정리 전에 캡처한다. 가시 피해처럼 한 틱에 같은 대상에 여러 번 발생하는 피드백은 합산할 수 있지만 판정 자체는 변경하지 않는다.

세션별 최근 32개 정도의 작은 이벤트만 보존하고 스냅샷에 복사한다. 틱마다 적 위치 전체나 이미지를 이벤트에 반복 포함하지 않는다. 이벤트를 보존하는 동안에도 롤·사망·턴 종료·승리 같은 중요한 사건이 연속 타격 장식에 밀리지 않도록 한 틱의 반복 피해를 합산한다. 실제 패킷 크기는 구현 검증에서 측정한다.

클라이언트는 세션별 가장 최근에 본 sequence를 유지한다. 첫 동기화에서는 현재 sequence를 기준점으로 잡고 과거 효과를 재생하지 않는다. 이후 sequence 순서로 새 이벤트만 처리한다. 같은 이벤트가 재전송돼도 다시 소리나 효과를 만들지 않는다. 사건은 원래 턴/층/플레이어의 장면 키에 연결한다. 최신 전투와 맞지 않는 타격 파편을 새 장면에 붙이지 않으며, 마지막 처치가 넘어갈 때는 짧은 클리어 배지에 그 결과를 담는다. 승리는 일반 클리어/턴 연출보다 우선한다.

페이지가 숨겨지거나 연결이 끊기면 입력 눌림·임시 효과를 정리한다. 다시 보일 때는 최신 상태로 기준점을 맞추고 지나간 연출을 몰아서 실행하지 않는다.

**대안:** 스냅샷 차이만 사용하는 방식은 하트 즉시 복구와 런타임 삭제를 놓친다. 모든 이벤트를 영구 저장하거나 별도 스트리밍 프로토콜을 도입할 필요는 없으므로 선택적 짧은 기록을 사용한다.

### 4. 주사위부터 도착까지 1초 안의 겹치는 연출

주사위는 눌림 → 굴림/대기 → 확정 눈 착지 → 탑 표식 이동 → 도착 배지의 표현 상태를 가진다. 실제 게임 phase와는 별개의 상태다. 서버가 확정하기 전의 면 변화는 장식이며 확정값으로 취급하지 않는다. 두 클라이언트 모두 확정 이후 같은 참가자의 이동을 표시한다.

| 순간 | 기본 표현 | 기준 시간 |
| --- | --- | --- |
| 버튼 활성화 | 눌림, 짧은 회전·면 변화, 버튼 잠금 | 다음 프레임부터 |
| 확인 응답 | 정확한 눈으로 착지, 한 번의 금빛 강조 | 140~250ms |
| 층 이동 | `이전 층 → 도착 층`, 탑 표식 상승, 짧은 계단음 | 응답 후 200~600ms |
| 층 도착 | 층 번호·종류 배지, 보스는 붉은 문양, 상점은 금빛 문양 | 응답 후 450~900ms |

연출은 겹쳐 전체 확인 후 구간을 900ms 안팎, 명세상 최대 1초로 제한한다. 정상적인 결과 표시 이후 전투는 즉시 조작 가능하다. 이동 표식이 움직이는 동안에도 확정 층 번호는 즉시 갱신하고 진행 중인 장식 숫자와 구분한다.

응답이 2초를 넘으면 끊임없는 회전을 멈추고 `서버 응답 대기`로 바꾼다. 임의 확정이나 자동 재전송을 하지 않는다. 거절·연결 종료·다른 턴 확정 시 pending 상태를 정리한다. 버튼은 현재 권한과 미해결 요청을 함께 고려한다.

탑 표시는 100개 행을 나열하기보다 10층 단위 눈금과 별도 두 참가자 레인을 가진 간결한 세로 표시로 구성한다. 초기 0층은 입구로 표시하고, 같은 층은 좌우로 분리한다. 이동 중에 지나친 10층은 실제 방문한 보스처럼 연출하지 않는다. 99+6은 눈 6과 도착 100을 명확하게 구분한다.

**대안:** 전체 화면 이동 컷신이나 새 `floor-setup` 대기 단계를 추가하면 현재 전투 타이머·CPU 흐름을 바꾸게 된다. HUD의 주사위/탑과 상단 도착 배지에 연출을 집중한다.

### 5. 전투 손맛은 짧은 반응과 명확한 실루엣

화면은 `activePlayer`의 전투를 선택한다. 관전자는 `CPU 관전`/`2P 관전`을 보고, 개인 자원과 관전 대상의 자원을 구분한다. 턴이나 층이 바뀌면 이전 보간과 전투 효과를 정리한다.

- 공격: 수락된 공격당 짧은 검 궤적/발사 반응, 실제 투사체의 잔상. 원거리 칼날은 기존 추가 투사체를 눈에 띄는 검기로 표현한다.
- 대시: 확정된 시작/끝 위치의 잔상과 먼지. 화염 대시는 실제 위험 장판과 장식 잔상을 구분한다.
- 타격: 약 80~120ms의 적 반짝임, 약 500ms 피해 숫자, 작은 파편. 보스/강한 피해는 강조하되 실제 넉백이나 월드 정지로 연결하지 않는다.
- 플레이어 피해: 지면 위치를 유지하는 짧은 스프라이트 반응, 하트 변화, 약한 화면 가장자리 강조. 선택적인 미세 흔들림은 약 2~3px/120ms로 제한하고 reduced-motion에서는 끈다.
- 보상: 상자 열림 프레임, 확정 코인량의 짧은 팝업, 획득 아이템 배지, 구매 시 비용 감소 표시, 물약의 회복 반응. 코인 입자는 자동 보상 위에 얹는 장식이지 새 획득 조건이 아니다.

장판·유령·충돌 지형은 효과와 구분해 읽히게 그린다. 카메라 흔들림을 쓸 경우 `pointerToWorld`가 렌더 변환을 역으로 적용해 마우스 조준을 보존한다. 서버에 보낼 aim은 장식 스프라이트 오프셋이 아니라 확정 지면 위치를 기준으로 계산한다.

**대안:** 물리 넉백·전역 hit-stop은 기존 전투 판정과 타이머를 바꾸므로 사용하지 않는다. 반응의 크기·지속시간·소리로 타격감을 만든다.

### 6. 전투 공간을 중심으로 HUD 재배치

전체 대시보드처럼 여러 큰 패널을 두기보다, 얇은 상단 상태 줄과 하나의 압축된 측면 HUD를 사용한다. 상태 줄에는 모드·방·참가자·턴, 측면에는 주사위·탑 진행·자원을 계층적으로 배치한다. 보스/위험 안내는 상단의 짧은 비차단 배지로 표현한다. 설명·로그는 접을 수 있는 도움말 영역으로 옮긴다.

1024×768과 1280×720에서 경기장과 주사위가 함께 읽히도록 제목·패딩·카드 크기를 줄인다. 좁은 화면은 레이아웃을 접되 모바일 전투 입력은 추가하지 않는다. 버튼의 키보드 포커스와 이름을 유지하고, 설정/입력 요소에 포커스가 있을 때 Space 등을 게임 키로 오인하지 않게 한다.

아이템은 기존 `ITEM_DEFINITIONS`로 이름·희귀도·가격·지속시간·위험 문구를 가져온다. 상세 설명은 짧은 텍스트/펼침 영역으로 제공해 공격 공간에 상시 긴 내용을 얹지 않는다.

**대안:** 기존 사이드바에 연출용 카드를 계속 추가하면 핵심 행동이 화면 아래로 밀린다. 재배치와 정보 공개 단계 조절을 선택한다.

### 7. 효과음과 접근성은 표현 시스템의 일부

기존 Web Audio 기반을 유지하되 주사위 탭/착지, 층 도착, 공격/타격, 코인, 회복, 위험, 패배, 승리를 짧은 서로 다른 envelope로 만든다. 사용자 클릭·키 입력에서 하나의 AudioContext를 준비/재개한다. 자동재생 차단을 오류로 취급하거나 게임 진행 조건으로 삼지 않는다.

설정은 `효과음`과 `연출 줄이기` 두 가지를 기본으로 한다. 저장 키는 버전이 있는 로컬 표현 설정 하나로 제한하고 저장 실패 시 메모리 설정으로 동작한다. 브라우저 `prefers-reduced-motion` 또는 로컬 연출 줄이기가 켜져 있으면 강한 움직임은 제거한다. 실행 중 설정 변경도 즉시 적용한다.

오디오도 이벤트 중복 제거 뒤 실행하며 동시 음성 수는 8개 정도로 제한한다. 연속 타격·장판 소리는 짧은 재생 간격을 두고, 위험 소리는 임계점 진입/유령 출현에 재생해 매 스냅샷·매 초 같은 경고가 반복되지 않게 한다. 모든 중요한 정보는 소리 없이도 읽히게 남긴다.

**대안:** 외부 음향 패키지나 큰 배경음 파일은 이 단계에 필요하지 않다. 생성형 짧은 효과음으로 시작하고 분위기 음악은 후속 변경으로 남긴다.

### 8. 효과와 리소스 예산

동시 장식 입자는 약 128개, 떠 있는 텍스트는 약 16개로 상한을 둔다. 보상·파편은 약 1초 안에 지우고 오래된 낮은 우선순위 효과부터 줄인다. 적 위치·유령·실제 위험 장판 등 gameplay 객체를 이 제한 때문에 제거하지 않는다. `requestAnimationFrame` 기준으로 프레임 시간을 측정해 일반 전투와 보스전의 효과 밀도를 조절한다.

원본 PNG 전체를 초기 로드하지 않는다. 사용할 이미지의 런타임 크기·압축 형태를 마련하고, 시작 화면/기본 캐릭터/주사위에 필요한 자산만 먼저 준비한다. 보스·상점 전용 리소스는 별도로 준비하며 실패 시 즉시 대체 표현을 쓴다. 목표는 초기 필수 이미지 약 3MiB 이하로 설정하고 실제 Pages 산출물의 파일별 크기를 기록한다. 엔진/프레임워크/대형 연출 라이브러리는 추가하지 않는다.

**대안:** 수 MB짜리 25개 원본을 그대로 모두 연결하면 첫 실행 비용이 너무 크다. 필요한 source 영역과 런타임 해상도를 가진 선별 리소스를 선택한다.

### 9. 호환성과 검증

새 클라이언트는 `presentationEvents`, `lastRoll`, `readyPlayers`가 없는 응답도 안전하게 처리한다. 이벤트가 없을 때는 관찰 가능한 phase/층/하트/코인 변화만 보수적으로 표현하며, 100층 상한 때문에 실제 눈을 알 수 없는 경우 주사위 숫자를 추측하지 않는다. 사망 복구를 회복으로 오인하는 애니메이션도 만들지 않는다. 알 수 없는 미래 이벤트 종류는 무시한다.

기존 세션 테스트로 규칙 보존을 확인하고 순수 이벤트 소비기/여정 상태기 테스트로 중복·최종 타격·사망·연속 턴·첫 동기화·누락 필드를 검증한다. 브라우저에서는 CPU 및 새로 만든 두 테스트 클라이언트 방만 사용한다. 준비/주사위/상점 버튼의 누르기·떼기 사이에 상태 갱신이 있는 상황, 실제 연출 중 이동/조준, 관전, reduced-motion, 음소거, 자산 실패, 낮은 뷰포트를 확인한다. CSS 속성 자체를 복제하는 단위 테스트는 만들지 않는다.

**대안:** 스크린샷만으로 승인하면 입력과 이벤트 중복 문제를 놓친다. 상태 경계 테스트와 실제 플레이 확인을 함께 사용한다.

## Risks / Trade-offs

- [입장 연출 중 전투 진행] → 모든 도착/턴 연출을 짧은 비차단 HUD 피드백으로 만들고 즉시 legal 입력을 허용한다.
- [원본 시트의 크기·발 위치 불일치] → 명시적 source rectangle/pivot을 사용하고 서 있는 상태·걷기·공격을 나란히 비교한다. 충돌 기준은 기존 지면 좌표로 고정한다.
- [서버/클라이언트 배포 시차] → 표현 이벤트를 선택 필드로 추가하고 구버전 응답 대체 표시를 검증한다. 실제 공개 서버의 새 필드 제공 여부를 별도로 확인한다.
- [동일 결과 재전송과 CPU의 빠른 턴] → sequence 중복 제거, 장면별 효과 연결, 최신 턴 우선 처리로 오래된 연출이 다음 행동을 막지 않게 한다.
- [패킷/프레임 비용 증가] → 작은 이벤트 기록과 입자/음성 상한을 두고, 전투 중 패킷 크기와 프레임 비용을 실제 측정한다.
- [강한 연출의 피로·위험 가림] → 낮은 기본 흔들림, 위험물 우선순위, reduced-motion, 음소거, 짧은 효과 수명으로 조절한다.
- [기존 규칙 명세와 코드의 일부 차이] → 다중 방 처리·층 입장 체력 등 기반 동작은 이번 변경에서 재정의하지 않는다. 기존 게임 테스트를 유지하며 표현에 필요한 결과만 연결한다.

## Migration Plan

1. 안정적인 HUD, 프레임 렌더링, 구버전 대체 경로와 표현 설정을 먼저 구현한다.
2. 선택적 서버 표현 이벤트를 연결하고 주사위/층 이동부터 전투/보상까지 단계적으로 켠다. 미연결 원본은 보존하고 검토한 런타임 리소스만 커밋 대상으로 삼는다.
3. 타입검사·기존/추가 테스트·프로덕션 빌드와 CPU/온라인 테스트 방 플레이를 확인한다.
4. 기존 GitHub Pages/Render 경로로 배포한다. Pages 성공뿐 아니라 Render 최신 서버가 표현 이벤트를 보내는지도 확인한다. 서버 재시작 시 기존 메모리 방이 사라지는 현재 제약을 고려한다.
5. 공개 페이지의 새 테스트 경기에서 주사위→도착→전투→턴 교대와 설정을 확인한다. Render 배포 권한/연결이 없는 경우 성공으로 간주하지 말고 구버전 대체 동작과 미완료 서버 반영을 구분해 기록한다.
6. 롤백은 표현 변경 커밋을 되돌리고 재배포한다. 선택 필드이므로 기존 클라이언트/서버와의 조합이 게임 규칙을 바꾸지 않는다. 데이터 마이그레이션은 없다.
